# macOS Command Adapter Process Contract

Contract version: `mac-command-process/v1`.

This contract defines process identity, stop and cleanup requirements for a later macOS command adapter described in the [MVP contract](contract.md). It specifies behavior; it does not claim that the adapter exists or that command-mode leases are enabled.

## Supported boundary

If enabled later, v1 is limited to the configured `mac.go-test` and `mac.swift-test` profiles under one configured macOS user. It adds no CLI, wire-protocol, or configuration fields. The adapter receives the already accepted command as an argument vector, passes it directly to the fixed helper without a shell, and does not persist or audit argv or inherited environment. Command text, executable names, and paths are never used to find or target a running process.

Both default Mac command pools remain closed in the current service. A raw `lease request` for either pool refuses with `adapter_required` before creating a waiter or lease. Process-group membership and `AbandonProcessGroup=false` do not prove that every attempt descendant is contained or stopped. Command acquisition stays disabled until a separately selected and reviewed macOS mechanism either prevents descendants from escaping the attempt scope or provides complete identity-safe discovery of that scope. An identity-discovery mechanism must be active before command start, cover descendant creation through reparenting and group/session changes, detect lost or overflowed observations, and close the descendant-creation window before the final empty proof. Its stop authority must exclude unrelated processes. A trusted-profile label or an expectation that commands stay in one group is not enforcement. If the mechanism is missing, unavailable, or cannot provide complete proof, refuse acquisition or keep the resource unavailable/quarantined.

A supported host must provide the domain/service-target form of `launchctl bootout --wait`. If the installed command does not accept that exact form, command-mode acquisition is refused. The blocking wait runs outside the request loop so status and unrelated resource tags remain serviceable; a blocked or incomplete cleanup never releases the resource.

## Attempt identity

Each command attempt has a random, never-reused attempt ID and an exact launchd service target made from the configured per-user bootstrap domain and a unique per-attempt service label. The label is the administrative identity and the only stop target. A label collision, missing domain, or inability to confirm the exact target refuses acquisition; an existing label is never taken over.

The attempt scope comprises the fixed helper and every process started by its command attempt; it excludes the lease coordinator/service and unrelated processes. The coordinator/service runs outside the attempt launchd job and owns durable attempt transitions, the stop receipt, and the final resource grant. The fixed helper runs inside the attempt job and is expected to terminate when the coordinator boots out that exact target. The helper never commits the stop receipt.

The launchd job invokes only the fixed adapter helper through `ProgramArguments`. The command argument vector travels through a launchd-managed local Unix socket with an explicit user-only mode (`0600`, plist integer `384`); the helper binds each request to the attempt ID. Launchd passes the socket descriptor to the helper, which passes argv directly to the command runner. This is a one-user boundary, not isolation among processes of that user. The job configuration must set `KeepAlive=false`, `AbandonProcessGroup=false`, and `ExitTimeOut=20` seconds explicitly. It must not place command arguments or inherited environment in the plist, lease database, audit record, or logs. The helper must verify before command start that its process group does not match the coordinator or another active attempt and contains no other process; otherwise it refuses the attempt. This startup check is only a contamination check: it neither prevents descendants from leaving the group nor unrelated same-session processes from joining later, and it never proves complete attempt containment.

Before command start, record the helper's current process observation tuple: PID, process start seconds and microseconds, UID, and process-group ID. XNU's `proc_bsdinfo` exposes those fields. A PID without its start-time tuple is not an identity. The tuple rejects stale observations after PID reuse, but it is a snapshot, not an atomic process handle; it never authorizes a PID-directed signal.

## Durable attempt state

The current service schema v1 remains manual-only and is not modified in place. Before command-mode implementation, a separate, explicitly versioned v1-to-v2 SQLite migration must add a `command_attempts` table. Startup never silently upgrades an existing database; command acquisition remains refused until the migration is installed and its exact schema is verified.

Each `command_attempts` row contains: `attempt_id` (128 random bits, lowercase hex, primary key, never reused), `lease_id` (unique reference to the lease), `launchd_domain`, `service_label` (unique with the domain), `helper_pid`, `helper_start_sec`, `helper_start_usec` (0 through 999999), `helper_uid`, `process_group_id`, `state` (`starting`, `running`, `cleanup_pending`, `quarantined`, or `stopped`), `stop_receipt_version` (null until proof succeeds, then 1), and nullable `attempt_scope_empty` and `cleanup_complete` booleans. `attempt_scope_empty=true` records complete proof for the defined attempt scope, never only an empty process-group query. Receipt fields remain null before stop proof and are set together to version 1 and true only after every stop and cleanup check succeeds. A `stopped` attempt requires that complete receipt. The coordinator writes the row as `starting` before the helper receives argv and updates it to `running` only after the helper tuple is recorded. It never contains argv, inherited environment, or child output. Process IDs are internal recovery metadata and never appear in audit or user-facing output.

Only the outside lease coordinator writes these states. The helper cannot write durable attempt state or a stop receipt after it has been stopped. The successful coordinator transaction atomically changes the attempt to `stopped` with receipt version 1, records complete attempt-scope proof and `cleanup_complete=true`, changes the lease to its terminal result, and makes the resource `available`. A transaction failure leaves the prior durable state fenced. A crash or restart that finds `starting`, `running`, or `cleanup_pending` without this receipt sets the resource to `quarantined`; absence of a receipt is never repaired by inference. A valid receipt is bound to exactly one attempt ID and launchd service target.

## Descendant discovery and stop

Parent-chain walking is insufficient: macOS changes a child's parent ID after its parent exits, while process-group membership is a separate field. Enumerate current members of the recorded process group with `proc_listpids(PROC_PGRP_ONLY, ...)` and read each current tuple with `proc_pidinfo`. This finds a reparented descendant that remains in the attempt group. It cannot find a descendant that has left that group, and an empty group result is not proof that the full attempt tree has stopped. Group enumeration is supplemental; it authorizes reuse only when the separately reviewed mechanism proves that the complete attempt scope is contained and observed. If a process-info read races with exit or PID reuse, retry from a fresh enumeration; if a complete consistent view cannot be obtained, stop proof is unavailable. A polling snapshot alone is insufficient unless the accepted mechanism closes the descendant-creation window and detects any coverage gap before the final proof.

On normal command exit, explicit release, or hard end:

1. Durably move the attempt and its resource to `cleanup_pending` before requesting any stop. The lease remains fenced from new grants until the successful stop transaction records its terminal result.
2. From the lease coordinator, which runs outside the attempt group, request `launchctl bootout --wait` for the exact `<domain>/<label>` service target. Do not address a PID, process-group number, executable name, command line, or path. The installed `launchctl help bootout` warns that `--wait` can block indefinitely; while it waits, the resource stays unavailable.
3. Require successful bootout completion and complete, identity-safe proof that no process in the attempt scope remains. Process-group enumeration alone is insufficient unless the accepted mechanism proves that no descendant can escape and no unrelated process can enter the stop scope. An empty or missing result caused by a failed, truncated, or inconsistent query is not proof. An unexpected or independently observed live descendant keeps the resource unavailable; never target an escaped PID separately.
4. Remove the attempt's temporary IPC and launchd configuration. If any cleanup step fails, keep the resource unavailable.
5. After the helper has stopped and proof plus cleanup succeed, the outside coordinator persists the stop receipt bound to the attempt ID and exact service label, records the lease's terminal result, marks the attempt `stopped`, and makes the resource `available` in one durable transaction. A transaction failure leaves the prior durable state fenced.

The `AbandonProcessGroup=false` launchd rule terminates remaining members of the job's process group when the job dies; it does not contain or discover descendants that escaped that group. `bootout --wait` completion and full attempt-scope proof are both required; neither the command's exit nor an empty-group observation alone proves that the process tree stopped. The helper's termination during this coordinator-initiated stop is expected and happens before receipt commit. The receipt is written by the outside coordinator, is internal recovery state rather than an audit payload, and contains no argv, environment, command output, boot-session UUID, or monotonic clock value.

## Refusal, crash, and restart behavior

Any failed or uncertain step—bootout refusal, a surviving attempt member, incomplete attempt-scope proof, PID/start-time mismatch, unexpected helper loss before the coordinator stop sequence, IPC or configuration cleanup failure, coordinator loss, or inability to persist the stop receipt—leaves the resource in `cleanup_pending` or quarantined. It never wakes a waiter or creates a second grant. The helper's expected termination after the coordinator requests bootout is not a failure; it also is not proof by itself.

If the outside coordinator/service dies before the receipt is durable, restart preserves the resource as unavailable or quarantined. A missing launchd job, an empty process-group list, or an absent helper is not a substitute for complete attempt-scope proof or a durable receipt. This contract defines no automatic recovery from a missing receipt; a separate, reviewed recovery decision is required.

## Required acceptance cases

These are implementation requirements, not claims that tests have run. Run them only in isolated disposable fixtures. Each negative case must assert no successful receipt, no second grant or waiter wake, and the required resource state, with a valid positive control.

| Case | Setup | Required result |
| --- | --- | --- |
| Positive verified full-tree stop | With a separately selected and reviewed containment or identity-proof mechanism active, a command creates a child and grandchild; the parent exits first and a descendant attempts to leave the initial process group or session. | Exact service-target bootout completes; independent identity proof confirms every process in the attempt scope stopped and no unrelated process was targeted; cleanup succeeds; the outside coordinator commits the receipt before the resource becomes available. This case must pass before command acquisition is enabled. |
| Unproven mechanism refusal | Request either default command pool while the complete attempt scope cannot be proved. | Return `adapter_required` before creating a waiter or lease; keep the command pool closed and do not wake a waiter. A valid manual-pool acquisition remains available. |
| Escaped/reparented survivor | An attempt descendant leaves the original group before the first enumeration, is reparented, and an independent liveness observer confirms it is still alive at the reuse decision. | Keep the attempt fenced or quarantined; write no successful receipt; do not grant the resource or wake a waiter. A complete empty original-group result is insufficient. |
| Discovery gap or late descendant | The identity-discovery mechanism loses coverage before the first observation, reports overflow, or a live attempt descendant can create a child after the final census starts. | Refuse successful proof and keep the resource fenced or quarantined; do not write a receipt, grant the resource, or wake a waiter. |
| Reused PID | Present a prior PID with a different start-time tuple, UID, or process group. | Treat the old observation as stale; never target that numeric PID. The attempt's unique service label remains the only stop target. |
| Same-name unrelated process | Run a separate process with the same executable basename outside the verified attempt scope. | Exact service-target bootout leaves it untouched; process names and command lines are not queried for targeting. |
| Missing or partial proof | Make a process query fail, truncate, or return inconsistent identity data. | Refuse completion; preserve the fence and do not wake a waiter. |
| Cleanup failure | Make removal of the attempt's IPC or launchd configuration fail after stop proof. | Keep the resource unavailable; do not write a successful stop receipt or wake a waiter. |
| Authorized helper stop | The helper belongs to the stopped attempt group and exits during coordinator-initiated bootout. | Treat helper termination as expected; after complete attempt-scope proof and cleanup, the outside coordinator commits the receipt and terminal lease/resource transition. |
| Unexpected helper loss | The helper exits before the coordinator has initiated the stop sequence. | Keep the attempt unavailable or quarantined; helper absence is not proof, and no receipt, second grant, or waiter wake occurs. |
| Coordinator loss before receipt | Stop proof and cleanup have not yet been durably committed when the outside coordinator exits. | Restart finds no valid receipt and keeps the resource unavailable or quarantined; no grant or waiter wake occurs. |
| Restart without proof | Restart with an attempt in `cleanup_pending` and no valid durable receipt. | Keep the resource unavailable or quarantined; do not infer success from the missing job or an empty best-effort observation. |
| Schema migration | Migrate a valid v1 database and verify all pre-existing lease state is preserved in v2. | A missing or malformed v2 attempt table refuses command acquisition and leaves the database and manual-pool state unchanged. |

Until the full-tree positive passes under the selected mechanism, command acquisition remains disabled. The current refusal control must confirm that a command-pool request returns `adapter_required` before creating a waiter or lease; a valid manual-pool acquisition remains the positive control for the first service slice. No process-group-only case proves full-tree containment.
