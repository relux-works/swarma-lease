# Resource Lease Contract and MVP

Date: 2026-11-13

## Product rule

A resource has one stable ID and one tag. Resources with the same tag form a pool. A request names one tag and a duration, joins that tag's FIFO queue if no resource is free, receives exactly one available resource ID, and releases the lease explicitly or at a fixed hard end. The first use is one Mac host's Go and Swift test slots.

## First-host defaults

The owner fixed these defaults on 2026-11-13:

| Setting | Default |
| --- | --- |
| `mac.go-test` pool | One resource: `go-test-01`. |
| `mac.swift-test` pool | One resource: `swift-test-01`. |
| OS-user boundary | One configured macOS user owns the service, database, socket, and wrapped commands. Other OS users cannot access them. Processes under the same OS user are equivalent; this is not per-agent isolation. |
| Maximum lease duration | 20 minutes. This preserves the current grant limit. |
| Maximum queue wait | 30 minutes. The value is required per waiting request and cannot exceed this cap. |
| Resource reuse after command | Reuse only after the wrapper confirms the command and its descendants have stopped and cleanup succeeds. Otherwise the resource stays unavailable or quarantined. |

These defaults are stored in SQLite. Adding a resource is an explicit `resource add` operation committed to SQLite. The v1 CLI has no file-based configuration or live limit-edit operation; a later limit change requires a separately versioned migration. Startup never silently increases a pool or extends a request.

## MVP boundary

The first implementation slice includes one Go service and CLI on one host, one local SQLite database, one local Unix-domain socket, resource registration/disable/enable/recovery, exact-tag requests, strict per-tag FIFO, blocking wait, explicit release, fixed hard end, status, audit history, and restart recovery.

The first slice does not execute commands. The two default Mac test pools are registered as `command` pools, and raw `lease request` calls for them refuse with `adapter_required` before creating a waiter or lease. This keeps those pools closed until the later command-adapter slice implements the stop-and-cleanup contract below. Core scheduling can be used with explicitly registered `manual` pools; these pools do not launch or supervise commands.

The next implementation slice adds `lease run` for the Go and Swift test pools. It starts the supplied argument vector without shell interpretation, enforces the lease hard end, and returns a command pool to service only after stop and cleanup are confirmed.

Multi-host allocation, network-filesystem state, priorities, preemption, multiple-resource requests, arbitrary capability expressions, recurring bookings, application credentials, remote TCP access, automatic hardware reset, and lease heartbeat/renewal are excluded. Processes running as the same configured macOS user are one authority boundary; the service does not isolate agents from each other.

## Names and admission

Accept tag and resource ID values only when they match `^[a-z0-9]+([._-][a-z0-9]+)*$`. This allows lowercase ASCII letters and digits separated by one `.`, `_`, or `-`; first and last characters are alphanumeric. Tags are case-sensitive and compared byte-for-byte. IDs are globally unique. No paths, URLs, whitespace, shell syntax, Unicode lookalikes, or empty values are accepted.

| Form | Expected result | Reason |
| --- | --- | --- |
| `mac.go-test` | Accept | Dotted tag for the first Mac Go test pool. |
| `mac.swift-test` | Accept | Dotted tag for the first Mac Swift test pool. |
| `qa.device` | Accept | Dotted tag for a manual device pool. |
| `qa.pool` | Accept | Explicit manual-pool example. |
| `go-test-01` and `swift-test-01` | Accept | Hyphenated resource IDs for the defaults. |
| `qa-01` | Accept | Hyphenated resource ID for a manual pool. |
| `ci_runner-01` | Accept | Underscore/hyphen form for a resource ID. |
| `Mac Go Test` | Reject | Uppercase and whitespace are outside the canonical form. |
| `../private` | Reject | Path traversal syntax is not a tag or ID. |
| `https://host/path` | Reject | URLs are not tag or ID values. |
| `x;command` | Reject | Shell metacharacters are not accepted. |
| Empty string or repeated separators | Reject | Empty components are invalid. |

The first slice must keep this boundary aligned with every legitimate tag and ID emitted by registration and configuration. Invalid syntax fails before state changes. A valid manual tag with no currently available resource may wait; an unknown tag fails immediately.

`resource add --tag TAG --id ID --mode manual|command` requires all three values; there is no implicit pool mode. A missing or unsupported mode is `invalid_pool_mode`. A new tag is registered with the specified mode. Adding another resource to an existing tag requires the same mode; a mode mismatch or duplicate resource ID refuses before writing. Pool mode is immutable for the lifetime of a tag in v1; use a new tag for a different mode.

## Local service, identity, and durable store

The service starts in the foreground with `swarma-lease serve` and listens only on `~/.swarma-lease/service.sock`. TCP is not supported. Resolve the home directory from the system account record for the effective UID; never trust a `HOME` environment override. The default state directory is `~/.swarma-lease`; it contains `leases.sqlite`, `service.lock`, and `service.sock`, plus SQLite WAL files while the database is open. SQLite is the only source of truth. V1 has no external configuration file: pool registration and resource control are database transactions, and the lease and wait limits are fixed at the defaults above.

If the state directory does not exist, `serve` creates its final path owned by the effective UID with mode `0700`; an existing final path is checked with `lstat` and is never chmodded or replaced. A directory/database/socket/lock owner mismatch or stored `owner_uid` mismatch returns `unsafe_state_path`; a mode other than exactly `0700` for the directory or exactly `0600` for the database, lock, WAL/SHM files, or socket, or a connecting peer UID mismatch, returns `permissions_invalid`. The service checks the connecting peer UID as well as the filesystem boundary. Symlinks, non-regular database/lock paths, wrong-owner paths, or paths with a mode other than the required exact mode are refused without following, unlinking, or chmodding the path. The service does not run as root. All processes under the configured user share lease authority; this is not per-agent isolation.

SQLite uses WAL on local storage, `synchronous=FULL`, foreign keys, and short `BEGIN IMMEDIATE` write transactions. A grant, timeout, cancellation, release, expiry, or resource transition is committed atomically before a success response or event is sent. A storage failure rolls back the whole transaction. The database has `PRAGMA user_version=1`; the `settings.schema_version` value must also be 1. V1 accepts only that exact schema version. A different version, failed `PRAGMA integrity_check`, or missing/invalid required table is refused as `state_incompatible` or `state_corrupt`; startup never guesses a migration or reseeds an existing database.

A new installation is created in a private temporary database file whose name is `.leases.sqlite.init-` plus 32 lowercase hexadecimal characters. Before bootstrap, the service must obtain and validate `CLOCK_REALTIME`, the current boot-session UUID, and continuous monotonic time; failure returns `clock_unavailable` without creating a database or socket. Bootstrap uses SQLite `DELETE` journal mode while it creates the full v1 schema, a settings row containing the current boot-session UUID, and two default command pools and resources in one transaction. It commits, closes SQLite cleanly, syncs the database file, atomically renames it to `leases.sqlite`, and syncs the state directory. Only after opening the final path does the service switch to WAL mode with `synchronous=FULL`, validate the schema, and create the socket. This avoids renaming a database while its WAL/SHM sidecars still use the temporary basename. Bootstrap inserts `mac.go-test` / `command` / `go-test-01` and `mac.swift-test` / `command` / `swift-test-01`; both resources start available with fencing token 0 and both per-tag queue counters start at 1. If the process stops before that rename, the next start holds the service lock and removes only the exact temporary database path and its `-journal` sibling when each is a regular, same-owner, mode-0600 file; it then repeats bootstrap. A matching symlink, wrong-owner/mode/non-regular path, or temporary WAL/SHM sidecar is refused and preserved (`unsafe_state_path` for an unsafe path, otherwise `state_corrupt`). No other filename or suffix is removed. If `leases.sqlite` is absent but a final-path journal, WAL, or SHM sidecar exists, startup refuses as `state_corrupt` and preserves the files. If the final database exists, it is authoritative and SQLite performs its normal WAL recovery before service recovery. A malformed final database is preserved and refused; it is never replaced with defaults. This makes first initialization resumable without a separate config/database pair.

The v1 persisted model is:

| Table | Fields and constraints |
| --- | --- |
| `settings` | Exactly one row with `singleton_id INTEGER PRIMARY KEY CHECK(singleton_id=1)`, `schema_version INTEGER CHECK(schema_version=1)`, `owner_uid INTEGER`, `max_lease_ns INTEGER CHECK(max_lease_ns=1200000000000)`, `max_wait_ns INTEGER CHECK(max_wait_ns=1800000000000)`, `boot_session_id TEXT CHECK(length(boot_session_id)=36)`, and `created_at TEXT`. `boot_session_id` is the validated OS boot-session UUID for the monotonic clock epoch currently represented by live deadlines. |
| `pools` | `tag TEXT PRIMARY KEY COLLATE BINARY`, `mode TEXT CHECK(mode IN ('manual','command'))`, `next_queue_sequence INTEGER CHECK(next_queue_sequence>=1)` starting at 1, and `created_at TEXT`. Mode never changes in v1. |
| `resources` | `id TEXT PRIMARY KEY COLLATE BINARY`, `tag TEXT REFERENCES pools(tag)`, `state TEXT CHECK(state IN ('available','leased','disabled','cleanup_pending','quarantined'))`, `fencing_token INTEGER CHECK(fencing_token>=0)` starting at 0, and `created_at TEXT`, `updated_at TEXT`. IDs are globally unique. Manual resources use only available, leased, or disabled. |
| `requests` | `request_id TEXT PRIMARY KEY COLLATE BINARY`; `tag TEXT`; `duration_ns INTEGER CHECK(duration_ns>0)`; `wait_mode TEXT CHECK(wait_mode IN ('wait','no_wait'))`; nullable `wait_timeout_ns INTEGER CHECK(wait_timeout_ns>0)`; nullable `queue_sequence INTEGER CHECK(queue_sequence>=1)`; nullable `queued_at TEXT`; nullable `wait_deadline_at TEXT`; nullable `queue_boot_session_id TEXT CHECK(length(queue_boot_session_id)=36)`; nullable `queue_started_monotonic_ns INTEGER CHECK(queue_started_monotonic_ns>=0)`; nullable `wait_deadline_monotonic_ns INTEGER CHECK(wait_deadline_monotonic_ns>0)`; `state TEXT CHECK(state IN ('queued','leased','released','expired','cancelled','timed_out','refused'))`; nullable `outcome_code TEXT`; `created_at TEXT`; `updated_at TEXT`. The tag is intentionally not a foreign key so a valid unknown-tag refusal can be retained. |
| `leases` | `id TEXT PRIMARY KEY COLLATE BINARY`, `request_id TEXT UNIQUE REFERENCES requests(request_id)`, `resource_id TEXT REFERENCES resources(id)`, `state TEXT CHECK(state IN ('active','released','expired'))`, `duration_ns INTEGER CHECK(duration_ns>0)`, `granted_at TEXT`, `hard_end_at TEXT`, `boot_session_id TEXT CHECK(length(boot_session_id)=36)`, `granted_monotonic_ns INTEGER CHECK(granted_monotonic_ns>=0)`, `hard_end_monotonic_ns INTEGER CHECK(hard_end_monotonic_ns>0)`, `fencing_token INTEGER CHECK(fencing_token>=1)`, nullable `ended_at TEXT`, nullable `ended_resource_state TEXT CHECK(ended_resource_state IN ('available','disabled','cleanup_pending','quarantined'))`, nullable `ended_fencing_token INTEGER CHECK(ended_fencing_token>=1)`, plus `CHECK((state='active' AND ended_at IS NULL AND ended_resource_state IS NULL AND ended_fencing_token IS NULL) OR (state IN ('released','expired') AND ended_at IS NOT NULL AND ended_resource_state IS NOT NULL AND ended_fencing_token IS NOT NULL))`. Lease IDs are 32 lowercase hexadecimal characters from 128 random bits. |
| `audit` | `sequence INTEGER PRIMARY KEY AUTOINCREMENT`, `at TEXT`, `operation TEXT`, nullable valid `request_id TEXT`, nullable valid `target_id TEXT`, `result_code TEXT`, nullable `from_state TEXT`, nullable `to_state TEXT`. It records committed state transitions and initial acquisition policy refusals that reserve a request key only. |

Except where the table marks a value nullable, columns are NOT NULL. The settings row has primary key value 1 and records the effective OS UID; startup requires the same UID. The owner UID is the effective UID of the first successful `serve` initialization. All UTC timestamps use the fixed representation below. Monotonic values are signed nanoseconds sampled from the OS continuous clock and are comparable only when their row's boot-session UUID matches the current OS boot session. Boot-session values are canonical hyphenated UUID strings. At startup, every queued request and active lease must match the persisted `settings.boot_session_id`; a malformed ID or mismatch within those live rows is `state_corrupt`. Terminal history retains each row's original boot-session ID. `queue_boot_session_id`, `queue_started_monotonic_ns`, and `wait_deadline_monotonic_ns` are either all null or all non-null; they are non-null exactly when the request entered the queue, and the deadline equals the sampled start plus `wait_timeout_ns`. An immediate grant has no queue sequence or queue timestamps. A waiting request that is immediately granted retains its wait mode and timeout input but never receives queue timestamps. A request that actually queues retains its sequence and all deadline values in terminal history. `wait_mode=no_wait` requires null `wait_timeout_ns`; `wait_mode=wait` requires a positive value. `queue_sequence`, `queued_at`, `wait_deadline_at`, `queue_boot_session_id`, `queue_started_monotonic_ns`, and `wait_deadline_monotonic_ns` are all null or all non-null. `granted_monotonic_ns` and `hard_end_monotonic_ns` are set together for every lease and retained with `boot_session_id` in terminal history. The required named indexes and unique column constraint are specified below. Startup verifies the required tables, columns, CHECK constraints, foreign keys, and indexes; an absent or mismatched item is `state_incompatible`, not a request to repair or reseed the database. Audit `operation` is one of `lease.acquire`, `lease.cancel`, `lease.release`, `resource.add`, `resource.disable`, `resource.enable`, `resource.recover`, `scheduler`, or `startup.recovery`. `result_code` is `ok` for a committed grant or successful resource operation; `request_timed_out` or `request_cancelled` for the corresponding request transition; `lease_released` or `lease_expired` for every request, lease, and resource transition caused by that lease ending; or the stable refusal code for an initial acquisition policy refusal. `audit.request_id` is the related request ID when one exists. `audit.target_id` is the exact ID of the object whose state changed: request ID, lease ID, or resource ID. `from_state` and `to_state` describe that object and are null only for a newly inserted row’s `from_state`. Queue sequence is allocated per tag in the same transaction that inserts a queued request; it starts at 1 and increases without reuse. The remaining schema and audit invariants are unchanged.

The store also enforces one active lease per resource, one lease per request, one request row per idempotency key, one immutable mode per tag, and unique queue sequence numbers per tag. Resource state is `leased` exactly while an active lease exists; request state is `leased` exactly while its associated lease is active. On release or hard end, the request and lease move to the same terminal state in the same transaction. An active lease has null `ended_at`, `ended_resource_state`, and `ended_fencing_token`; a released or expired lease has all three set in its terminal transaction. The ended-resource fields are an immutable snapshot used by terminal lookup/replay, so a later lease on the same resource cannot change the result of an earlier lease query. `ended_fencing_token` equals the lease's `fencing_token`; `ended_at` is the service time sampled in the transaction that ends the lease. `refused` always has a non-null `outcome_code`; `queued` and active `leased` have a null `outcome_code`; terminal request outcomes are `request_timed_out`, `request_cancelled`, `lease_released`, `lease_expired`, or the refusal code that caused `refused`. A resource's fencing token increments in the same transaction as every grant; it starts at 1 on the first grant and is never reused. All SQLite INTEGER counters are signed 64-bit; `MAX_INT64` is 9223372036854775807. `next_queue_sequence` starts at 1 and never wraps. If it is MAX_INT64, a wait request that needs a new queue position is terminally refused as `queue_sequence_exhausted`; no sequence is allocated and existing queue rows remain unchanged. Immediate grants and no-wait requests do not consume a queue sequence. If the audit AUTOINCREMENT reaches MAX_INT64, the write transaction rolls back and the service returns `storage_unavailable`. A lease may increment a resource token from MAX_INT64-1 to MAX_INT64; when that lease ends, the resource moves to disabled instead of available. A disabled resource at MAX_INT64 cannot be re-enabled; add a new resource ID for replacement. Queue and audit records are retained for the lifetime of the database; V1 exposes no purge operation. Request input equality is checked using the stored canonical fields, not by trusting a hash alone. Every timestamp is formatted as `YYYY-MM-DDTHH:MM:SS.NNNNNNNNNZ`.

The rows above are the complete durable state model. Resource registration through `resource add` writes the pool and resource rows in one transaction, so the database governs the next restart. The boot-session and monotonic columns are internal recovery data and are omitted from socket responses, events, history output, CLI JSON, and logs; the defined UTC projection fields remain visible. Limits cannot be edited in V1. Any future limit or schema change requires a separately specified and versioned migration. V1 rejects unknown user tables, columns, indexes, and triggers; SQLite internal objects required for declared constraints and AUTOINCREMENT are allowed. The exact additional indexes are `CREATE UNIQUE INDEX requests_tag_queue_sequence ON requests(tag, queue_sequence)` and `CREATE UNIQUE INDEX leases_one_active_resource ON leases(resource_id) WHERE state='active'`; `leases.request_id` is a unique column constraint.

## Unix-socket protocol

The socket carries UTF-8 JSON Lines. Each frame is one JSON object followed by LF; a frame payload is at most 65,536 bytes excluding LF. CRLF is accepted as a line ending and removed before decoding. JSON object keys must be unique. Empty frames, invalid UTF-8/JSON, duplicate keys, non-integer numeric fields, and oversized frames are rejected before database changes: malformed/empty/unterminated JSON is `invalid_json`, a payload over the limit is `frame_too_large`, and a valid JSON value with a field of the wrong type is `invalid_request`. Input may arrive fragmented or several complete lines may be coalesced; the service processes lines in order. A client sends its next operation only after the previous operation completes. For a blocking operation, the queued response is not completion; the client waits for its terminal event before sending another frame on that connection. A long wait occupies that connection.

Every socket request is one JSON object with exactly these top-level fields: `version`, `type`, `op`, and `data`, plus `request_id` only for `lease.acquire`, `lease.wait`, and `lease.cancel`. `version` is an integer, `type` is exactly `request`, `op` is one of the operation names below, `data` is an object, and request IDs are strings matching the grammar in Request identity. JSON key order has no meaning. Operation-specific `data` keys and their types are exact as listed below; no aliases or unknown fields are accepted. Integer fields are JSON integers in decimal notation, not strings, fractions, exponents, or booleans.

Example:

```json
{"version":1,"type":"request","op":"lease.acquire","request_id":"req-01","data":{"tag":"qa.pool","duration_ns":1200000000000,"wait_mode":"wait","wait_timeout_ns":1800000000000}}
```

Every synchronous response has exactly these fields: `version`, `type`, `op`, optional `request_id`, `state`, `data`, and optional `code`. `version` is integer 1 and `type` is exactly `response`. The response `request_id` is the valid acquisition/wait/cancel key, or the valid request-ID lookup from `lease.status`; it is absent for unrelated operations and invalid IDs are never echoed. Successful responses have no `code`; their `state` values and `data` shapes are fixed below. Error responses have `state:"error"`, a stable `code`, and an object `data`; the error-data shapes are fixed in Refusal codes. There is no free-text message field. A refusal never echoes the rejected JSON, invalid field value, command, environment, or filesystem path. An unsupported integer version is refused as `unsupported_version`. For a request with a recognized `op`, responses echo that operation; malformed frames, undecodable JSON, and unrecognized operation names use `op:"protocol"`. CLI-only errors use the recognized service operation when one is known, otherwise `op:"cli"`. The service emits one error then closes the connection after a malformed frame. For a blocking operation it does not process a later buffered frame until the terminal event has been sent.

A blocking acquisition first receives `state:"queued"` with the request ID and queue sequence when it has not yet received a resource. The server then sends exactly one terminal event on that connection:

```json
{"version":1,"type":"event","name":"lease.granted","request_id":"req-01","sequence":12,"data":{"request":{"request_id":"req-01","tag":"qa.pool","duration_ns":1200000000000,"wait_mode":"wait","wait_timeout_ns":1800000000000,"queue_sequence":1,"queued_at":"2026-11-13T17:00:00.000000000Z","wait_deadline_at":"2026-11-13T17:30:00.000000000Z","state":"leased","outcome_code":null},"lease":{"id":"00000000000000000000000000000001","request_id":"req-01","tag":"qa.pool","resource_id":"qa-01","state":"active","duration_ns":1200000000000,"granted_at":"2026-11-13T17:00:00.000000000Z","hard_end_at":"2026-11-13T17:20:00.000000000Z","fencing_token":1,"ended_at":null,"ended_resource_state":null,"ended_fencing_token":null},"resource":{"id":"qa-01","tag":"qa.pool","mode":"manual","state":"leased","fencing_token":1}}}
```

The other terminal event names are `request.timed_out` and `request.cancelled`; their request record contains the stable terminal `outcome_code`. The `sequence` references the audit row for the request state transition that produced this event; it remains unique when the same transaction also records lease and resource transitions. A broken socket can lose an event after the state is committed. The client then reconnects by request ID and reads the persisted result. Multiple connections may observe one request; each receives the same snapshot/result. Disconnecting one observer never cancels the request or changes another observer's result.

The complete operation surface is:

| `op` | Required request fields | Success `state` | Success `data` |
| --- | --- | --- | --- |
| `lease.acquire` | Top-level `request_id`; data: `tag`, positive `duration_ns`, `wait_mode` (`wait` or `no_wait`); `wait_timeout_ns` is required only for `wait`. | `granted` or `queued`. | Request-result object. A queued result is followed by one terminal event on that connection. |
| `lease.wait` | Top-level `request_id`; empty data object. | `granted` or `queued`. | Request-result object. It only looks up and observes the existing request; it does not take or compare acquisition fields, create a queue entry, or change the original deadline. A queued result is followed by one terminal event on that connection. |
| `lease.cancel` | Top-level `request_id`; empty data object. | `cancelled`. | Request-result object for the newly cancelled request. A repeated or non-queued cancellation follows the terminal/error rules below. |
| `lease.release` | Data: `lease_id`; no top-level request ID. | `released` or `expired`. | Request-result object with the resource snapshot from the lease's terminal transaction. Releasing an ended lease again succeeds with the same terminal records. |
| `lease.status` | Data: exactly one of `lease_id` or `request_id`; no top-level request ID. | The looked-up request state or lease state. | Request-result object; never allocates or changes a lease. A refusal stored on a request is returned as data with no error code. |
| `resource.add` | Data: `tag`, `resource_id`, `mode` (`manual` or `command`) | `added`. | `pool` object (`tag`, `mode`) and the resource record after scheduling. It runs the scheduler in the same transaction before replying; an older waiter may already have leased the new resource. |
| `resource.disable` | Data: `resource_id` | `disabled`. | `resource` record. Repeating disable on an already disabled resource is an idempotent success; a leased resource cannot be disabled. |
| `resource.enable` | Data: `resource_id` | `enabled`. | `resource` record after scheduling. Repeating enable on an available resource is an idempotent success. Enabling a disabled resource runs the scheduler in the same transaction before replying; an older waiter may already have leased it. A resource at MAX_INT64 fencing token refuses as `invalid_transition`. |
| `resource.recover` | Data: `resource_id`, `confirm_stopped:true` | `recovered`. | `resource` record after scheduling. It returns a quarantined command resource to available only after the operator has confirmed stop and cleanup outside the service; a resource at MAX_INT64 fencing token is recovered to disabled. |
| `service.status` | Empty data object. | `ok`. | `schema_version`, `owner_uid`, `max_lease_duration_ns`, `max_wait_timeout_ns`, `pools`, and `counts`. |
| `audit.list` | Data: `limit` from 1 to 100; optional positive `before_sequence`. | `ok`. | `entries` array with at most `limit` allowlisted audit rows in ascending sequence order, older than the optional cursor. |

Any missing/extra field, operation-field mismatch, absent top-level request ID for `lease.acquire`, `lease.wait`, or `lease.cancel`, or a top-level request ID supplied to another operation is `invalid_request`, except wait-mode/timeout and pool-mode values use their dedicated codes below. `lease.status` uses the lookup `request_id` inside `data`. The CLI maps `lease request` to `lease.acquire`, `lease wait` to `lease.wait`, `lease cancel` to `lease.cancel`, `lease release` to `lease.release`, `lease status` to `lease.status`, and `history` to `audit.list`; its `--id` flags map to the corresponding `resource_id` or `lease_id` field. The CLI and socket API use the same operation and result definitions; the CLI does not expose a second service protocol.

The JSON record objects and operation data are fixed as follows:

| Result | Exact data fields |
| --- | --- |
| Request record | `request_id`, `tag`, `duration_ns`, `wait_mode`, nullable `wait_timeout_ns`, nullable `queue_sequence`, nullable `queued_at`, nullable `wait_deadline_at`, `state`, and nullable `outcome_code`. Request ID is 1–128 ASCII bytes matching `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`. |
| Lease record | `id`, `request_id`, `tag`, `resource_id`, `state`, `duration_ns`, `granted_at`, `hard_end_at`, `fencing_token`, nullable `ended_at`, nullable `ended_resource_state`, and nullable `ended_fencing_token`. Lease ID is exactly 32 lowercase hexadecimal characters. |
| Resource record | `resource` object with `id`, `tag`, `mode`, `state`, and `fencing_token`. |
| `lease.acquire`, `lease.wait`, `lease.cancel` | `request` record, nullable `lease` record, and nullable `resource` result. |
| `lease.release` | `request` record, `lease` record, and the resource record captured by the terminal lease transaction. |
| `lease.status` by request ID | `request` record, nullable `lease` record, and nullable `resource` result. |
| `lease.status` by lease ID | `request` record, `lease` record, and `resource` result. |
| `service.status` | `schema_version`, `owner_uid`, `max_lease_duration_ns`, `max_wait_timeout_ns`, `pools`, and `counts`. Pools are sorted by tag; each pool has `tag`, `mode`, and resources sorted by ID. Each resource has the fields in Resource result. Counts has `queued_requests`, `active_leases`, `terminal_requests`, and `audit_rows`; `terminal_requests` counts released, expired, cancelled, timed_out, and refused requests. |
| `audit.list` | `entries` array; each entry has exactly `sequence`, `at`, `operation`, nullable `request_id`, nullable `target_id`, `result_code`, nullable `from_state`, and nullable `to_state`. |

Every request-result `data` object includes all three keys `request`, `lease`, and `resource`; inapplicable records are JSON null. A grant includes all three records. For an active lease, `resource` is the current resource record. For a terminal lease, `resource` is reconstructed from the immutable `ended_resource_state` and `ended_fencing_token` snapshot, so retries return the same terminal data even if the resource has since been reused. A terminal event has exactly `version`, `type:"event"`, `name`, `request_id`, `sequence`, and `data`, where `data` is the same request-result object. The `lease.granted` event includes the committed lease and resource; timeout/cancel events use null for lease and resource. Valid state-dependent acquisition refusals include the persisted Request record and null lease/resource. `request_id_conflict` and `request_not_cancellable` include the existing committed Request result, never the conflicting input. Syntax and transport failures use an empty `data` object. Every timestamp uses the exact UTC format in Time and scheduling; all IDs and integer fields keep the types specified above.

## CLI surface

The first slice supports only these commands:

```text
swarma-lease serve
swarma-lease resource add --tag qa.pool --id qa-01 --mode manual --json
swarma-lease resource disable --id qa-01 --json
swarma-lease resource enable --id qa-01 --json
swarma-lease resource recover --id qa-01 --confirm-stopped --json
swarma-lease lease request --tag qa.pool --duration 20m --wait --wait-timeout 30m --json
swarma-lease lease request --tag qa.pool --duration 20m --no-wait --json
swarma-lease lease wait --request-id req-01 --json
swarma-lease lease cancel --request-id req-01 --json
swarma-lease lease release --id 00000000000000000000000000000001 --json
swarma-lease lease status --request-id req-01 --json
swarma-lease lease status --id 00000000000000000000000000000001 --json
swarma-lease service status --json
swarma-lease history --limit 50 --before-sequence 100 --json
```

All management commands require `--json` and write exactly one JSON object plus LF to stdout. A blocking request or wait command consumes the final terminal event and prints only its final JSON result; it does not print the intermediate queued response. `serve` is the only command without `--json`; it writes sanitized startup/shutdown/error records to stderr. Unknown flags, duplicate flags, and a missing `--json` are rejected before connecting to the service with `invalid_request`, an empty data object, and `op` set to the recognized operation (or `cli` when no operation can be resolved). No request bytes are sent. There is no `--state-dir`, network, shell, process-name, polling, or config-file override in V1.

For `lease request`, callers must supply exactly one of `--wait` or `--no-wait`. `--wait-timeout` is required with `--wait` and forbidden with `--no-wait`. Missing or conflicting wait modes are `invalid_wait_mode`; a missing, forbidden, malformed, zero, or negative wait timeout is `invalid_wait_timeout`. `--request-id` is optional for the initial CLI command; if omitted, the CLI generates 128 random bits with `crypto/rand` and encodes them as 32 lowercase hexadecimal characters before opening the service connection. The CLI includes the final request ID in every result. `lease wait` takes no new wait timeout.

The duration grammar for `--duration` and `--wait-timeout` is a positive base-10 integer followed by one of `ns`, `us`, `ms`, `s`, `m`, or `h`; signs, decimals, spaces, and Unicode micro symbols are rejected. The exact integer nanosecond value is sent over the socket. A syntactically valid number that overflows signed 64-bit nanoseconds is `invalid_duration`; a representable value above the configured cap is `duration_exceeds_max` or `wait_exceeds_max`. `history --limit` defaults to 20 and accepts 1 through 100; `--before-sequence` is an optional positive audit sequence cursor. With a cursor, the service selects the newest `limit` entries strictly below it, then returns them in ascending sequence order; without a cursor, it returns the newest `limit` entries in ascending order. Every command except `serve` uses the JSON response schema above, including local syntax and transport errors. The client emits no success message on stderr.

On client interruption before a complete response, the CLI emits exactly one JSON response with `state:"error"`, `code:"client_interrupted"`, exit 130, and `data:{"attempt_state":"not_sent"}` if it can prove no request-frame bytes were written by this invocation, or `data:{"attempt_state":"unknown"}` otherwise. `not_sent` describes only this invocation and does not claim that a supplied idempotency key has no earlier record. The CLI includes the original or generated `request_id` for a key-bearing operation; a generated key exists before connecting. Any frame write, including a queued acknowledgement followed by interruption, yields `unknown`; a caller resolves a lease request by that key. The CLI sends no implicit cancellation, release, retry, or second frame. The interruption itself changes no service state; already-sent work and normal scheduler transitions may still commit. The request remains queued until explicit cancellation or its original monotonic deadline; a committed lease remains active until release or its monotonic hard end. If the complete terminal response was read before the signal is handled, the CLI emits that normal result instead. The CLI never prints a grant until it has read a committed grant response/event.

## Time and scheduling

The deadline clock is macOS `mach_continuous_time()`, converted to signed nanoseconds with the OS timebase. It advances during system sleep and is not changed by wall-clock corrections ([Apple API](https://developer.apple.com/documentation/kernel/mach)). Each UTC timestamp is sampled from `CLOCK_REALTIME` for audit and display; `wait_deadline_at = queued_at + wait_timeout` and `hard_end_at = granted_at + duration` are frozen UTC projections made when the operation is queued or granted, and are not authoritative deadlines. The service reads the current OS boot-session UUID with `sysctlbyname("kern.bootsessionuuid")` into `settings.boot_session_id`; persisted monotonic deadlines are compared only within that boot session. Each state-changing transaction samples both clocks once and uses the continuous sample for expiry/grant decisions. If either sample is unavailable, the transaction rolls back and returns `clock_unavailable`. The 30-minute wait cap bounds grant eligibility; OS scheduling may delay recording or sending the timeout result, but every grant path rechecks monotonic time and cannot grant at or after the deadline.

For a queued request, `wait_deadline_monotonic_ns = queue_started_monotonic_ns + wait_timeout_ns`. At `monotonic_now >= wait_deadline_monotonic_ns`, the request becomes `timed_out` before the scheduler considers any grant or cancellation. A resource released or enabled exactly at the deadline cannot be granted to that expired request. For a lease, `hard_end_monotonic_ns = granted_monotonic_ns + duration_ns`; at `monotonic_now >= hard_end_monotonic_ns`, it is expired before allocation or explicit release. A release at or after hard end therefore succeeds with state `expired`, not `released`. These comparisons are inclusive at the deadline. UTC display projections do not change when the wall clock changes and do not affect either comparison.

One scheduler transaction samples monotonic time once and performs these steps in order: expire overdue leases; expire queued requests at or past their deadline in queue-sequence order; make resources from ended manual leases available, or disabled if their fencing token is MAX_INT64; disable any available resource already at MAX_INT64; then grant the oldest eligible waiter the lowest-ID available resource. It also samples `CLOCK_REALTIME` for UTC audit/display fields. Every valid acquire, wait, cancel, release, or resource mutation runs in a `BEGIN IMMEDIATE` transaction that first performs this due-work pass before replaying a result or applying the operation. On a successful state-changing operation, any following scheduling pass is part of that same transaction; no competing operation can observe an intermediate resource state. If the requested operation refuses after the due-work pass, due transitions still commit, but the refused operation applies no requested transition and the error data/effect table describes that direct result. A later operation cannot revive or cancel a request that has already reached its monotonic deadline. A status/history read returns the latest committed snapshot and does not itself trigger or defer the scheduler. The transaction commits all related request, lease, resource, fencing-token, and audit changes together. Scheduling runs after a new request is persisted, resource add/recovery/enable, release, cancellation, a timeout wake, and startup recovery. A queued request cannot be bypassed by a newer request. Separate tags have independent FIFO queues.

For a wait request, the service persists its timeout before acknowledging `queued`; the deadline begins at that transaction's `queue_started_monotonic_ns`, not when the caller receives the response. It must be positive and no more than 30 minutes. Reconnect never accepts a replacement timeout. The original queue sequence and monotonic deadline survive process restart and multiple observers. Because the continuous counter has a boot-scoped epoch, a reboot expires every queued request before any new grant instead of comparing values from different boots or starting a new allowance. Service downtime within one boot still counts toward the original deadline. There is no polling API.

A duration must be positive and no more than the configured 20-minute maximum. The lease hard end begins at the committed grant time, not queue entry. The service never clamps or extends a duration. A reboot expires any lease from the previous boot before new grants, applying the existing resource-mode end and cleanup transitions. V1 has no heartbeat or renewal.

## Pool and resource state

A tag is created with the mode of its first resource and retains that mode for life. Every added resource must use the same mode. V1 has no mode-change or resource-delete operation. Adding a resource with a duplicate ID or a different mode refuses before writing.

Resource transitions are:

| Pool mode | Transition |
| --- | --- |
| Manual | `available → leased → available` on explicit release or hard end while the fencing token is below MAX_INT64; when it reaches MAX_INT64 the terminal transition is to disabled. `available → disabled → available` through disable/enable unless the token is MAX_INT64. |
| Command | `available → leased`; at hard end or explicit release, the lease ends and the resource enters `cleanup_pending`. Only a confirmed stop and successful cleanup return it to available, unless the fencing token is MAX_INT64, in which case it becomes disabled. Unknown/failed cleanup leaves it quarantined. A quarantined command resource returns to available only by explicit operator recovery after the operator has confirmed it safe; at MAX_INT64 it remains disabled. Raw acquisition is refused in V1, so the first slice cannot enter the command lease path. |

Pool availability is derived from its resources; there is no separate pool-disable state or pool-disable command:

- If every resource is disabled, a new manual-pool acquisition is refused as `pool_disabled`; it creates a terminal idempotency result and no waiter. Existing queued requests remain queued until their original deadline or an enable.
- If only some resources are disabled, enabled resources may be granted. If no enabled resource is currently available, a wait request joins the FIFO queue and a no-wait request returns `no_wait_busy`.
- If resources are leased, cleanup-pending, or quarantined and none is available, the pool is busy. A wait request queues; a no-wait request returns `no_wait_busy`.
- Enabling a resource invokes scheduling in the same transaction. The oldest eligible waiter gets the newly available capacity before the enable response is sent. Disabling a leased resource refuses without changing either resource or lease state.

`resource.disable` accepts `available → disabled` and is an idempotent success when already disabled; other source states return `invalid_transition`. `resource.enable` accepts `disabled → available` and is an idempotent success when already available below MAX_INT64; leased, cleanup-pending, quarantined, or MAX_INT64 resources return `invalid_transition`. `resource.recover` requires a command resource in `quarantined` state and `confirm_stopped:true`; any other state returns `invalid_transition`, and missing or false confirmation is `invalid_request`. Recovery moves it to available, or to disabled at MAX_INT64. Unknown resource IDs return `unknown_resource`.

A raw `lease request` for any command-mode tag always refuses as `adapter_required`, whether it waits or not and regardless of resource availability. This check has precedence over capacity checks. The two default Mac slots are command pools, so raw requests cannot lease them in the first slice. Manual leases do not start, stop, or supervise a process.

## Request identity, retries, cancellation, and commit

A request ID is 1 to 128 ASCII bytes matching `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`. It is a correlation/idempotency key, not a secret; callers must not put credentials or sensitive values in it. Tags and resource IDs are identifiers, not secret storage; callers must not put credentials, command text, environment values, or raw user data in any identifier. Each key is reserved for the lifetime of the database and is never pruned in V1.

The canonical acquisition input is the byte-exact tag, duration in integer nanoseconds, wait mode, and wait timeout (null for no-wait). A repeated `lease.acquire` with the same canonical input returns the original state; a repeated acquire with different input returns `request_id_conflict` and leaves the stored request untouched. `lease.wait` and `lease.cancel` take only the key and never supply or compare acquisition input. The CLI generates an ID before its first send so a lost reply can be resolved.

Syntax and field validation happen before a key is reserved. A syntactically valid key and request are recorded atomically with the state-dependent result. The following valid state-dependent refusals reserve a terminal key and replay the same code forever: unknown tag, duration/wait limit exceeded, command-mode `adapter_required`, all-resources-disabled `pool_disabled`, and immediate `no_wait_busy`, plus `queue_sequence_exhausted` when a wait request needs a queue position. This prevents retrying one key from changing a refusal into a later lease. A caller wanting a new attempt uses a new key. Invalid JSON, unsupported protocol, malformed names/IDs, invalid duration grammar/value, invalid wait flags, and unknown operation/fields do not reserve a key or change the database.

A queued request is one durable request row with one queue sequence. Repeating `lease.acquire` with the same ID and identical canonical input, or calling `lease.wait` with that ID, observes the existing row; it does not create another waiter or reset its deadline. A request whose ID was already used with different acquire input refuses. A committed active grant replays the exact same lease and fencing token. If that lease is released or expired, acquisition/wait retries return `lease_released` or `lease_expired` and never allocate another lease. Timed-out, cancelled, busy, disabled, unknown-tag, adapter-required, over-limit outcomes replay their terminal result. `lease.status` reads any existing lifecycle as a successful query with its state and outcome code; it never allocates. A status query succeeds with exit 0 for queued, leased, refused, cancelled, timed-out, released, and expired states; its `outcome_code` reports any terminal result.

Disconnect is not cancellation. The queue entry remains until its deadline or an explicit `lease.cancel`. Multiple same-user clients may observe one key. Each connection with an outstanding `lease.acquire` or `lease.wait` receives its own queued response and exactly one terminal event if it remains connected; a disconnected observer receives nothing and does not affect other observers. A lookup made after the request is terminal returns a synchronous result or stable terminal error and no event. The connection that successfully issues `lease.cancel` receives its synchronous cancellation response; other connected observers receive `request.cancelled`. There is no claim/acknowledgment step: once a grant transaction commits, the lease exists and is active whether or not any observer received the response. Cancelling is serialized with grant in SQLite. If cancellation commits first, the request becomes cancelled and cannot be granted. The first cancellation of a queued request succeeds with state `cancelled`; a repeated cancellation returns `request_cancelled` and the same terminal records. Cancelling a timed-out or refused request returns its stored terminal outcome. If grant commits first, cancellation returns `request_not_cancellable` and the committed lease result; it never releases a grant delivered to another client. A granted lease remains non-cancellable even if it is later released or expired.

The service sends success only after commit. A database rollback confirmed before commit creates no grant, waiter, or transition and returns `storage_unavailable` if storage caused the failure. If SQLite reports an outcome that cannot establish whether commit completed, or commit succeeds but the response/event is lost, the CLI reports `result_unknown` (exit 69), which makes no claim that a grant is absent. The client reconnects with the same ID using `lease status` or `lease wait`; the service returns the committed state. A connection failure known to happen before any request bytes were sent is `daemon_unavailable`. If a request frame has been partially or fully written and the client reads no final response, the result is unknown unless a complete service error response was received. This distinction prevents a transport failure from being reported as proof that no durable grant exists.

## Startup, shutdown, and recovery

If the state directory is absent, startup creates it owned by the effective UID with mode `0700`; it never follows a symlink while resolving or creating the directory. Startup validates the state directory, opens or creates `service.lock` without following symlinks, verifies its owner/type/mode, and acquires an exclusive advisory lock before examining the socket. A lock-file creation race is resolved by reopening and validating the one resulting path. The lock file is persistent and is never removed during normal shutdown. A held lock returns `instance_running`. After acquiring it, the service validates the v1 database, reads `CLOCK_REALTIME`, the boot-session UUID, and continuous monotonic time, and completes restart recovery before accepting clients or creating a socket. If any clock read fails or the UUID is invalid, startup returns `clock_unavailable` without changing database state or creating the socket.

If `service.sock` is absent, the service binds it and verifies owner and mode. An existing symlink, non-socket, or wrong-owner socket is `unsafe_state_path`; a same-owner socket whose mode is not exactly `0600` is `permissions_invalid`. Both paths are preserved without following, unlinking, or chmodding them. For an existing same-owner mode-0600 socket, the service attempts a local connect while holding the lock. A successful connect or any result other than connection-refused is live or uncertain and returns `socket_stale_uncertain` without unlinking. Only connection-refused plus a second `lstat` proving the exact same device/inode/owner/mode is a proven stale socket; the service may unlink that socket and bind. The new socket's device/inode are recorded. On shutdown, the service unlinks only that same socket inode if it is still a same-owner socket. It never unlinks another path.

Graceful SIGINT/SIGTERM stops accepting new requests, closes observer sockets, preserves queued requests and active leases, removes only its own socket inode, then releases the lock. Disconnecting observers does not cancel queued requests. After validating the database, startup reads the OS boot-session UUID and continuous monotonic time before any state transition. When the stored and current boot-session UUIDs match, restart recovery expires work at its original monotonic deadline; a service restart never renews the allowance. When they differ, one startup-recovery transaction expires every queued request as `request_timed_out`, ends every active lease as `lease_expired`, applies the existing per-pool resource transition, and updates `settings.boot_session_id` before any grant. Thus manual resources return to available or disabled by the existing fencing rule, and command resources enter `cleanup_pending` or remain quarantined; reboot does not bypass stop or cleanup requirements. All terminal rows retain their original boot-session IDs. If the boot-session UUID or continuous clock cannot be read or validated, startup refuses with `clock_unavailable`, creates no service socket, and leaves existing database state unchanged.

A database that cannot be opened, verified, or transactionally recovered causes `serve` to refuse startup with `storage_unavailable`, `state_corrupt`, or `state_incompatible`; it creates no service socket and preserves all state files. V1 has no in-place database repair command. Recovery requires stopping the service, taking a byte-for-byte backup of the full state directory, then restoring a known-good backup or obtaining an explicit versioned migration. Never delete, truncate, or reseed an unreadable existing database.

## Audit and privacy

The database is the only persistent state. Persisted fields are limited to the schema above: validated tags/IDs, request IDs, durations/deadlines, queue and fencing counters, states, lease/resource associations, terminal resource snapshots, safe result codes, and audit transitions. The request table stores canonical lease fields but no raw JSON. The audit table stores only operation name, valid IDs, result code, and state transition. One audit row is written for each persisted request, lease, or resource state transition, and for each initial valid acquisition policy refusal that reserves a request key. Rows from one transaction commit or roll back together and share that transaction's sampled time. Replays, ID conflicts, lookups, invalid transitions, resource-registration refusals, syntax errors, and transport errors do not add audit rows. It never stores command text or environment.

Service logs contain only timestamp, severity, and fixed event/error code. CLI errors contain only the stable code and the JSON fields defined above; no free-text message is emitted. Neither service nor CLI records or echoes raw frames, rejected values, command arguments, inherited environment, credentials, tokens, or full home/socket paths. Malformed syntax is refused without an audit row. Only committed state transitions and initial valid acquisition policy refusals that reserve a request key are audited; repeats, lookups, conflicts, and other refusals are not. `audit.list` exposes only the allowlisted audit columns. The first slice does not capture command output. The later adapter's explicitly requested stdout/stderr forwarding is a separate behavior and must not persist or audit child output, arguments, or environment.

## Refusal codes, exit status, and precedence

JSON error `code` values are stable API values. Error responses have no message field and never interpolate untrusted input. The response `request_id` is the valid acquisition/wait/cancel key, or the valid request-ID lookup from `lease.status`; it is absent for unrelated operations. The CLI maps service codes to these exit statuses. Every error response has `state:"error"`; the `Request ID` column specifies whether `request_id` is present, and `Error data` specifies the exact `data` object shape. `request-result` means the `request`, `lease`, and `resource` fields defined above, with inapplicable records null. Durable-effect rows describe the direct operation result; the required due-work scheduler pass may also commit its own overdue transitions before returning an error.

Successful management and lease operations exit 0. Replaying an ended lease through `lease.acquire` or `lease.wait` exits 4 so it cannot be mistaken for a usable grant; `lease.status` and idempotent `lease.release` exit 0 for terminal state. Repeating cancellation returns the stored terminal outcome code. A child-command exit status is not used in V1 because `lease run` is excluded.

Refusal precedence is fixed. First, the OS permission/path check occurs before protocol handling. Then frame/JSON validation, protocol version, operation name, exact field set and types, name/ID/duration and pool-mode grammar, wait-flag and wait-time validation, and operation-specific values such as `resource.recover.confirm_stopped=true` are checked before state changes. Next, the service samples both clocks and expires due leases and queue heads before idempotency replay or a new operation result. For an acquisition, an existing ID is then compared: identical input replays its stored state; different input returns `request_id_conflict`. For a new valid ID, policy checks run in this order: `duration_exceeds_max`; `wait_exceeds_max`; unknown tag; command-mode `adapter_required`; all-resources-disabled `pool_disabled`; busy `no_wait_busy` for no-wait mode; for wait mode, process older queued requests first and grant immediately when this request is next and capacity is available, without consuming a queue sequence. If both duration and wait exceed their caps, the request is refused once as `duration_exceeds_max`; each single-over-limit input retains its corresponding code. If it must join the queue and the tag counter is MAX_INT64, return `queue_sequence_exhausted`; otherwise enqueue. Before selection, any available resource already at MAX_INT64 is transitioned to disabled. On release or hard end, a resource whose fencing token is MAX_INT64 becomes disabled instead of available. `resource.enable` refuses it as `invalid_transition`. Thus invalid wait flags on a command pool return `invalid_wait_mode`, not `adapter_required`. If a policy refusal has an idempotency key, its refusal row and audit event commit in the same transaction. Every refusal has one result and the durable effect shown above. For non-acquisition operations, exact field/type/value validation precedes target lookup, and target lookup precedes source-state transition checks; thus malformed input wins over an unknown resource, and an unknown resource wins over `invalid_transition`. For `resource.add`, a duplicate resource ID wins over a valid-tag pool-mode mismatch. `resource.recover` validates `confirm_stopped:true` before target lookup. An invalid `audit.list` limit or cursor is `invalid_request`.

These cases are the implementation oracle, not results. Each positive case has a neighboring refusal/control; the service and CLI must use independent fixtures so a matching client/server mistake cannot pass.

## First production slice and later command adapter

The first implementation slice is a Go CLI and service for one Mac host, SQLite-backed resource and lease state, a versioned local-socket protocol, blocking FIFO wait, manual-pool hard-end handling, restart recovery, audit/status, stable refusal codes, and the one-user boundary. Its acceptance target is one valid manual-pool acquisition/release path plus the protocol, storage, time, idempotency, cancellation, error, pool-control, restart, and privacy cases above. Both default Mac test pools are registered in command mode and reject raw requests as `adapter_required`.

The first slice does not execute commands. The later command adapter adds `lease run --tag TAG --duration DURATION [--wait --wait-timeout TIMEOUT | --no-wait] -- COMMAND ARG...`. It passes an argument vector directly, with no shell interpretation. Normal command exit and explicit release end the lease only after stop and cleanup are confirmed. At hard end, the lease becomes expired and the resource enters `cleanup_pending`; no queued request can receive that resource until confirmed stop and cleanup. The adapter may stream child stdout/stderr to the caller while the command runs as separate streams; those bytes are opaque child output, not service JSON, and are never persisted or audited. The final lease result is emitted only after stop and cleanup are confirmed. The adapter must not persist command arguments or inherited environment.

The adapter is not pinnable for implementation from this first-slice contract. Before any command-mode lease is enabled, a separately reviewed contract must define process identity with PID-reuse protection, descendant discovery including reparented descendants, and the exact termination targets. Searching or killing by process name/pattern is forbidden; a same-name unrelated process must remain untouched. A same-user `lease release` cannot make a command resource available by itself: it first enters `cleanup_pending`, and only adapter stop proof plus successful cleanup returns it to available. A surviving or uncertain descendant, adapter death, restart without proof, or missing stop evidence leaves the resource unavailable/quarantined. Reuse requires proof that the identified command and all descendants stopped and cleanup succeeded. Acceptance must include a positive full-tree stop control and negative controls for a reparented survivor, reused PID, same-name unrelated process, and missing proof. No text here claims that those process-stop rules have already been implemented or accepted.
